# Repository Guidelines

Перед работой прочитай [руководство для агента](docs/GUIDE.md):
там находятся инструкции по установке, применению, обновлению и удалению
скиллов этого репозитория. Правила контрибьюта описаны ниже.

## Project Overview

`agents-flow` — коллекция независимых Markdown-скиллов для coding-агентов,
а не приложение. Скиллы задают процедуры написания, исправления и ревью кода;
языковые руководства адаптируют Google Style Guides, Docker содержит отдельные
рекомендации по образам.

## Architecture & Data Flow

- Источник пакета — `skills/<name>/SKILL.md`. YAML frontmatter `name` и
  `description` задаёт идентичность и область активации; имя каталога совпадает
  с `name`. Изменение описания может изменить поведение выбора скилла.
- `SKILL.md` содержит workflow и ссылки на локальные ресурсы. Восемь пакетов
  используют `references/google-guide.md`; Docker самодостаточен. Общего
  исполняемого слоя и зависимостей между пакетами нет. `git-guide` содержит
  отдельные references по истории, коммитам, изоляции и восстановлению.
- Поток: каталог в `README.md` → выбор по актуальному frontmatter → установка
  целых выбранных пакетов по `docs/GUIDE.md` из одной ревизии → discovery
  harness → загрузка подходящего `SKILL.md` и нужных references → работа
  с проектом пользователя и отчёт о фактических проверках.
- Не путай инструкции и примеры для потребляющего проекта с исходниками или
  командами этого репозитория. Async, DI, состояние и обработка исключений
  не реализованы здесь как программные подсистемы.

## Key Directories

- `skills/` — одиннадцать пакетов: `git-guide`, `init`, `dockerfile-styleguide`,
  `go-styleguide`, `python-styleguide`, `html-css-styleguide`,
  `shell-styleguide`, `typescript-styleguide`, `swift-styleguide`,
  `vimscript-styleguide`, `markdown-styleguide`.
- `skills/*/references/` — подробные правила, источники, атрибуция и адаптации.
  Ресурсы принадлежат пакету; сохраняй относительные ссылки при установке.
- `docs/` — инструкции агенту по установке, применению, обновлению и удалению.
  Каталогов приложения `src/`, тестов и исполняемых скриптов сейчас нет.

## Development Commands

Сборка, запуск приложения, автоматические test/lint-команды не настроены.
Не выдумывай `npm test`, `bun run build` или установщик.

Перед изменениями проверь рабочее дерево и создай отдельную ветку:

```sh
git status --short --branch
git switch -c feat/implement-{name}-skill
# Для исправления вместо feat-ветки:
git switch -c fix/{name}-skill
```

`{name}` замени коротким kebab-case именем задачи, например `markdown`.
После проверки значимого законченного шага добавь только относящиеся к нему
файлы и сделай коммит, например:

```sh
git add skills/markdown-styleguide/SKILL.md README.md docs/GUIDE.md
git commit -m "feat: implement markdown skill"
```

Не выполняй команды из примеров скиллов ради проверки документации.

## Code Conventions & Common Patterns

- Для Markdown применяй `skills/markdown-styleguide/SKILL.md` и его reference:
  один H1, ATX-заголовки, подписанные fenced blocks, содержательные ссылки;
  обычный текст переноси примерно на 80 колонках без ломания URL и примеров.
- Сохраняй русский язык README/GUIDE и английский язык существующих скиллов.
- Повторяющийся workflow: исследовать контекст и совместимость → различить
  ревью без записи и точечное исправление → применить правила проекта раньше
  базового стиля → выполнить существующие подходящие проверки → сообщить
  результат и ограничения. Не добавляй зависимости только ради стиля.
- Не меняй молча frontmatter, публичные anchors, команды, контракты и область
  активации. Синхронизируй правила `SKILL.md` и связанных references.
- Сохраняй источники, pinned revisions, даты, атрибуцию и лицензии. Отделяй
  upstream-правила от адаптаций; лицензия Swift отличается от остальных
  Google Style Guides, проверяй её по собственному reference.

## Contribution Workflow / Init

1. Перед любыми изменениями всегда создавай отдельную ветку
   `feat/implement-{name}-skill` или `fix/{name}-skill`; не работай в `main`.
   Сохраняй пользовательские изменения и не включай их в свои коммиты.
2. Прочитай затронутый скилл, references и документацию. Правь пакет целиком
   в пределах задачи, а не вводи второй параллельный набор правил.
3. При достаточно значимых изменениях всегда обновляй **оба** файла:
   `README.md` и `docs/GUIDE.md`. К таким изменениям относятся добавление,
   удаление, переименование, изменение назначения скилла или процедуры
   установки/применения. Согласуй каталоги, ссылки и примеры с frontmatter.
   Для локальной правки без изменения пользовательского поведения не нужны
   формальные правки этих документов.
4. Каждое достаточно значимое завершённое действие закрепляй отдельным
   проверенным коммитом: например, законченный пакет с документацией или
   самостоятельное исправление. Не оставляй всю работу одним отложенным
   коммитом и не коммить незавершённые промежуточные состояния.

## Important Files

- `README.md` — пользовательский каталог и примеры запросов.
- `docs/GUIDE.md` — основной контракт установки и использования.
- `skills/*/SKILL.md` — точки входа, activation metadata и процедуры.
- `skills/*/references/google-guide.md` — детальные правила и provenance.
- `skills/dockerfile-styleguide/.editorconfig`, `.gitattributes`, `.gitignore`
  — настройки только Docker-пакета, не всего репозитория. EditorConfig задаёт
  UTF-8, LF и финальный перевод строки; Markdown исключён из trimming.

## Runtime/Tooling Preferences

Обязательного runtime, package manager, manifests, lockfiles или CI нет.
Не навязывай Bun, Node, Python, Docker или компилятор из-за названия скилла.
Для работы нужны текстовые файлы и Git; выполнение скиллов зависит от harness.

Устанавливай только выбранные пакеты целиком в документированный каталог
текущего harness. Не клонируй репозиторий внутрь discovery roots, не запускай
скрипты ради установки инструкций и не затирай локальные адаптации.
Стандартные OMP-пути описаны в GUIDE, но требуют проверки версии и overrides.

## Testing & QA

Тестового framework, fixtures, coverage-порогов и автоматического QA pipeline
сейчас нет. Проверяй изменённый пакет и документацию:

- непустые `name`/`description`, уникальность имён и соответствие каталогу;
- наличие локальных ресурсов, правильность относительных ссылок, согласованность
  каталогов README/GUIDE и сохранность атрибуции;
- иерархию заголовков, закрытые fences, примеры и anchors в целевом renderer;
- отсутствие временных файлов, отчётов и лишней вложенности в пакете.

Для изменений установки отдельно проверь фактический discovery в harness:
копирование файлов не доказывает обнаружение. Если проверить нельзя, явно
сообщи это. Проверка существования ссылки не доказывает корректность fragment,
доступность удалённого URL или поведение скилла. Не заявляй о неисполненных
проверках и не устанавливай новый tooling только ради документации.
