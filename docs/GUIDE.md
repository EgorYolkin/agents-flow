# Руководство для агента

Установи выбранные пользователем скиллы из
[EgorYolkin/agents-flow](https://github.com/EgorYolkin/agents-flow) и проверь,
что текущий harness обнаруживает их. Затем применяй их только к подходящим
задачам. Это руководство предназначено агенту, выполняющему установку.

## 1. Определи контекст

Прочитай инструкции рабочей среды и проекта. Выясни:

- какой агент или harness используется и какая версия установлена;
- для какого проекта нужны скиллы и какие языки в нём используются;
- какие скиллы и пользовательские настройки уже существуют;
- пользователь хочет установку для текущего проекта или для всех проектов.

Используй доступный контекст и настройки. Не проси пользователя повторять уже
известное. Если harness или область установки не определены, задай короткий
вопрос до записи файлов в каталог установки.

### Настрой лимит контекста текущего harness

До установки скиллов проверь настройки контекста в том harness, где работаешь:
Codex, Claude Code, OMP, Pi, OpenCode или любом другом. Не переноси имена
параметров и способы настройки из одного harness в другой.

1. Определи версию harness, активную модель и эффективный лимит контекста
   текущей сессии. Проверь доступные сведения сессии и конфигурацию с учётом
   переопределений. Максимум модели не равен настроенному лимиту harness.
   Не угадывай значение по названию модели; если его нельзя установить,
   сообщи об этом и не меняй настройки вслепую.
2. Если эффективный лимит больше **250 000 токенов**, найди актуальную
   официальную документацию для установленной версии: как ограничить контекст,
   включить автоматическую компактизацию и задать её порог. Предпочитай
   Context7, когда он доступен; иначе используй официальные источники.
3. Документированным способом установи лимит **250 000 токенов** и порог
   автоматической компактизации **80%** этого лимита, то есть **200 000 токенов**.
   Проверь единицы и семантику параметра: процент заполнения, число токенов
   или резерв до лимита — разные настройки. Не подставляй `80` или `200000`
   без проверки документации. Если исходный лимит не превышает 250 000,
   оставь настройки контекста и компактизации без изменений.
4. Предпочитай настройку текущей сессии. Если доступно только сохранение
   в конфигурации, выбери минимальную подходящую область, сохрани остальные
   значения и локальные изменения. Выполни обязательное подтверждение записи,
   если его требует harness; не обходи ограничения разрешений.
5. Проверь эффективные значения после применения, а не только содержимое
   файла. Если нужен перезапуск, объясни это пользователю и не прерывай сессию
   автоматически. До проверки после перезапуска считай применение
   неподтверждённым.

Если harness не поддерживает ограничение контекста или нужный порог
компактизации, не придумывай параметры и не заменяй их ограничением ответа
модели. Выполни поддерживаемую часть, укажи оставшееся ограничение и ссылку
на документацию. В отчёте назови исходный лимит, изменения, область настройки,
источник инструкции и фактически проверенные итоговые значения.

## 2. Согласуй набор скиллов

Прочитай актуальные `skills/*/SKILL.md` из выбранной ревизии репозитория.
Бери имя и описание из YAML frontmatter. Не полагайся только на имя папки
или приведённую ниже таблицу: состав репозитория может измениться.

| Каталог в репозитории | Имя скилла | Область |
|---|---|---|
| `init` | `init` | Создание и обновление contributor guide `AGENTS.md` |
| `dockerfile-styleguide` | `dockerfile-styleguide` | Dockerfile и `.dockerignore` |
| `python-styleguide` | `python-styleguide` | Python: стиль, импорты, типы, docstrings и ответственность функций |
| `html-css-styleguide` | `html-css-styleguide` | HTML, CSS, шаблоны |
| `shell-styleguide` | `shell-styleguide` | Bash и POSIX sh |
| `typescript-styleguide` | `typescript-styleguide` | TypeScript и TSX |
| `swift-styleguide` | `swift-styleguide` | Swift |
| `vimscript-styleguide` | `vimscript-styleguide` | Vimscript |
| `markdown-styleguide` | `markdown-styleguide` | Markdown-документация |

Предложи небольшой набор по стеку пользователя и объясни назначение каждого.
Дождись явного выбора. Например:

> Для этого проекта подходят TypeScript, Shell и Docker. Markdown можно добавить
> для документации. Какие установить: предложенный набор, набор с Markdown или
> другой список? Установить только для этого проекта или для всех проектов?

Если пользователь уже назвал точный набор и область установки, считай выбор
согласованным. Не устанавливай остальные скиллы «на всякий случай».

## 3. Найди поддерживаемый каталог установки

Проверь механизм skills именно у текущего harness. Используй его установщик,
если он подходит для выборочной установки, либо документированный каталог.
Для актуального синтаксиса обращайся к документации, предпочитая Context7,
когда он доступен. Не считай один путь универсальным для всех агентов.

Для Oh My Pi документация указывает следующие стандартные пути:

| Область | Каталог |
|---|---|
| Пользовательская | `~/.omp/agent/skills/<skill-name>/SKILL.md` |
| Проектная | `<project-root>/.omp/skills/<skill-name>/SKILL.md` |

Учитывай пользовательские переопределения каталога и конфигурации установленной
версии. В стандартных roots OMP ищет скиллы на один уровень ниже `skills/`;
лишняя вложенность вида `skills/agents-flow/<skill-name>/SKILL.md` не подходит.
Если skills отключены, копирование файлов само по себе не включит их.
[Документация skills OMP](https://github.com/can1357/oh-my-pi/blob/main/docs/skills.md),
[пути конфигурации](https://github.com/can1357/oh-my-pi/blob/main/docs/config-usage.md).

Для другого harness отдельно проверь discovery, приоритет проектной и глобальной
установки, требования к имени и способ обновления списка скиллов. Не меняй
конфигурацию другого агента по аналогии с OMP.

## 4. Подготовь выбранные пакеты

Получи репозиторий в отдельную временную или уже согласованную рабочую папку.
Не клонируй весь репозиторий внутрь каталога установки skills. Зафиксируй SHA
полученной ревизии; все выбранные пакеты бери из одной ревизии. Не выполняй
скрипты из репозитория ради установки текстовых инструкций.

Для каждого выбранного пакета:

1. Проверь `SKILL.md`, его `name`, `description` и локальные ссылки.
2. Подготовь пакет целиком: `SKILL.md`, `references/` и другие ресурсы, если
   они существуют и используются скиллом. Сохрани атрибуцию источников.
3. Не включай `.git`, отчёты проверок, временные файлы и документацию по
   установке самого репозитория. Не создавай в каталоге skills папки
   `*-workspace` и HTML-отчёты.
4. Используй имя из frontmatter как имя установленного каталога, если harness
   не требует другого формата. В этом репозитории имена скиллов совпадают
   с именами каталогов.
   Исходную папку репозитория и frontmatter при этом не переименовывай.

Пример результата установки двух выбранных скиллов:

```text
<skills-root>/
├── dockerfile-styleguide/
│   └── SKILL.md
└── shell-styleguide/
    ├── SKILL.md
    └── references/
        └── google-guide.md
```

## 5. Установи без потери локальных изменений

До копирования проверь существующие назначения и совпадения имён в других
активных roots. Разные копии одного скилла могут скрывать друг друга.

- Если пакет отсутствует, установи подготовленную копию.
- Если содержимое совпадает, оставь его и сообщи, что установка уже актуальна.
- Если содержимое отличается и пользователь не согласовал замену, покажи
  существенные различия и уточни действие: сохранить, заменить или объединить.
  Не затирай локальные изменения молча.

При согласованной замене сохрани резервную копию вне всех каталогов discovery.
Проверь подготовленный пакет до подмены; не оставляй частично записанную
установку. Не удаляй другие пользовательские скиллы и не меняй настройки
форматтеров, CI или разрешений в рамках установки.

## 6. Проверь установку

Для каждого выбранного скилла проверь:

- `SKILL.md` доступен в правильном каталоге;
- frontmatter содержит непустые `name` и `description`;
- локальные ссылки ведут к скопированным ресурсам;
- нет случайной дополнительной вложенности и конфликтующей активной копии;
- harness показывает скилл в доступном списке либо позволяет явно загрузить его.

Обнови discovery документированным способом. Если нужен перезапуск сессии,
объясни это пользователю; не прерывай его текущую работу автоматически.
Если в текущей сессии нельзя проверить discovery, сообщи отдельно: файлы
установлены, обнаружение после перезапуска ещё не подтверждено.

Не заявляй, что скилл работает, только на основании успешного копирования.
Проверка установки не требует сборки пользовательского приложения, установки
линтеров или изменения исходников.

Заверши установку коротким отчётом: выбранные имена, область и фактические пути,
SHA источника, выполненные проверки и необходимое действие пользователя,
если оно осталось. Дай один пример запроса для его стека.

## 7. Применяй скиллы в задачах

Для подготовки инструкций репозитория используй `init`: исследуй фактическую
структуру, команды, тесты и историю, затем создай или обнови `AGENTS.md`
с заголовком `Repository Guidelines`. Ориентир — 200–400 слов. Сохраняй полезные
существующие правила; не выдумывай команды, coverage-пороги и PR-требования.
Это отдельная задача после установки: установка `init` сама по себе не означает
создание или перезапись инструкций проекта.

1. Определи языки и типы затронутых файлов. Учитывай shell без расширения,
   встроенные языки, шаблоны и TSX.
2. Загрузи подходящий `SKILL.md` штатным механизмом harness. Если такого
   механизма нет, явно прочитай файл и необходимые ссылки из `references/`.
   Не загружай все языковые руководства в каждую задачу.
3. Прочитай правила проекта и конфигурации существующих инструментов.
   Сохрани публичные API, формат данных и заявленную совместимость.
   Отступления от Google объясняй как решения проекта.
4. Различай режимы: ревью или объяснение — без записи; создание или исправление
   — точечные изменения в пределах запроса.
5. Запускай подходящие существующие проверки. Не устанавливай новые зависимости
   только ради стиля и не называй проверку выполненной, если она не запускалась.
6. Проверь итоговый diff. Сообщи существенные изменения или замечания,
   результаты проверок и реальные ограничения проверки.

Для смешанной задачи сочетай скиллы по областям: например, Docker для образа
и Shell для entrypoint. Не распространяй правила одного языка на другой.
Для Python используй `python-styleguide`: сначала проверь поддерживаемые версии
и существующие инструменты проекта. Сохраняй публичные API и не превращай
рекомендации по длине функций в обязательное разбиение или создание классов.
Обычная фраза «используй shell-styleguide» — запрос агенту, а не универсальная
команда терминала; конкретный синтаксис вызова зависит от harness.

Если работу выполняет subagent, явно передай ему нужный скилл, правила проекта,
область изменений и критерии результата. Не предполагай, что он автоматически
наследует все инструкции родительской сессии.

## 8. Обновляй и удаляй по запросу

Обновляй только выбранные пользователем пакеты. Зафиксируй новую ревизию,
сравни изменения инструкций и ресурсов, сохрани локальные адаптации, затем
повтори проверку установки. Не обновляй скиллы незаметно во время обычной задачи.

При удалении установи точный путь и область. Удали только запрошенный пакет;
не затрагивай исходный репозиторий, другие skills и резервные копии без отдельного
указания. После удаления проверь discovery или объясни необходимость обновить
сессию.
