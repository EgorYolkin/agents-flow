# Руководство для агента

Установи выбранные пользователем скиллы из
[EgorYolkin/agents-flow](https://github.com/EgorYolkin/agents-flow) и проверь,
что текущий harness обнаруживает их. Затем применяй их только к подходящим
задачам. Это руководство предназначено агенту, выполняющему установку.

Если репозиторий уже клонирован, читай это руководство и остальные документы
из его локальной папки `docs/`, а не через внешние URL. Если расположение копии
неизвестно, уточни путь у пользователя. Используй пакеты из этой же ревизии.

Подробные шаги установки вынесены в [отдельное руководство](INSTALLING_GUIDE.md).
Ниже сохранены ссылки на разделы для совместимости существующих ссылок.

## 7. Применяй скиллы в задачах

Для Git-процесса используй `git-guide`: установи исходное состояние и владение
изменениями, выбери ветку задачи и обеспечь одного писателя на директорию.
При необходимости используй отдельный worktree. Сохраняй законченные шаги
проверенными коммитами в рамках поручения; установка скилла сама по себе
не поручает менять репозиторий. Push, merge и release следуют отдельно
установленным полномочиям. Историю, изоляцию и восстановление читай
в соответствующих references по необходимости.

Для подготовки всего проекта к работе агента используй `init`: исследуй
архитектуру, команды, тесты, инструкции и Git, затем создай или аккуратно
обнови `AGENTS.md` с заголовком `Repository Guidelines` (ориентир — 200–400
слов) и проектный `GIT_WORKFLOW.md`. Последний — редактируемое место для
правил Git; в `AGENTS.md` должна быть ссылка с указанием читать workflow перед
Git-операциями. В пакет скилла входит только `GIT_WORKFLOW_EXAMPLE.md`,
пример структуры и стиля, а не готовая политика для всех проектов.

При первом init сообщи пользователю, что работаешь с Git и сохраняешь
законченные шаги коммитами по принятому workflow. Сначала определи реальный
корень, состояние Git и существующие соглашения. Если проект уже входит
в родительский репозиторий или worktree, не создавай вложенный `.git`.
Если репозитория действительно нет, инициализируй локальный Git; не добавляй
автоматически все существующие файлы и не создавай remote.

По умолчанию сохраняй процесс проекта: прочитай инструкции, существующий
workflow и небольшую выборку истории; не выдавай единичный пример за правило.
Если пользователь явно просит «с моими Git-правилами», загрузи актуальный
`git-guide` через текущий harness, а не копируй его правила в `init`.
Если скилл недоступен, сообщи о недостающем источнике и запроси его расположение
или правила; независимое исследование проекта можно закончить без выдумывания
пользовательской политики.

Сохраняй чужие staged/unstaged/untracked изменения, проверяй весь кандидат
коммита и эффективную идентичность автора. Коммить законченные проверенные
шаги, а не каждый вызов инструмента; один писатель работает в одной директории.
Параллельным писателям нужны отдельные worktree или последовательный запуск.
Локальные коммиты не означают разрешения на push, merge, release или
переписывание опубликованной истории.

Установка `init` сама по себе не запускает подготовку проекта. Запрос только
на ревью или черновик не разрешает создавать файлы, Git-репозиторий и коммиты.
Не выдумывай команды, coverage-пороги и PR-требования; сохраняй полезные
существующие правила.

1. Определи языки и типы затронутых файлов. Учитывай shell без расширения,
   встроенные языки, шаблоны и TSX.
2. Загрузи подходящий `SKILL.md` штатным механизмом harness. Если такого
   механизма нет, явно прочитай файл и необходимые ссылки из `references/`.
   Не загружай все языковые руководства в каждую задачу.
3. Прочитай правила проекта и конфигурации существующих инструментов.
   Сохрани публичные API, формат данных и заявленную совместимость.
   Отступления от Google объясняй как решения проекта.
4. Различай режимы: ревью или объяснение — без записи; создание или исправление
   — точечные изменения в пределах запроса.
5. Запускай подходящие существующие проверки. Не устанавливай новые зависимости
   только ради стиля и не называй проверку выполненной, если она не запускалась.
6. Проверь итоговый diff. Сообщи существенные изменения или замечания,
   результаты проверок и реальные ограничения проверки.

Для смешанной задачи сочетай скиллы по областям: например, Docker для образа
и Shell для entrypoint. Не распространяй правила одного языка на другой.
Для Python используй `python-styleguide`: сначала проверь поддерживаемые версии
и существующие инструменты проекта. Сохраняй публичные API и не превращай
рекомендации по длине функций в обязательное разбиение или создание классов.
На примерах из reference проверь, сохраняют ли аннотации связь входа и
результата, а docstring — смысл параметров и поведение на границах.
Предлагая класс, укажи, каким состоянием он владеет и какое правило защищает.
Начинай с решения для текущего вызова в существующем модуле, а не со слоёв
и интерфейсов на будущее. Для новых имён учитывай назначение и область
видимости; не переименовывай публичные параметры только ради стиля.
Применяй выбранное пользователем оформление функций, методов и классов:
обе строки `"""` отдельно от текста, пустая строка после docstring, смысловые
блоки разделены пустой строкой, связанные операции и их `if` остаются рядом.
После проверки с досрочным выходом отделяй основной путь пустой строкой;
так же отделяй изменение состояния объекта от последующего `return`.
Это адаптация скилла, а не требование Google. При конфликте с явными правилами
целевого проекта или его инструментами сообщи о нём; не меняй настройки молча.
Обычная фраза «используй shell-styleguide» — запрос агенту, а не универсальная
команда терминала; конкретный синтаксис вызова зависит от harness.

Для Go используй `go-styleguide`. Проверь версию языка в `go.mod` и вызовы
изменённого API. По сигнатуре и комментарию должно быть понятно, какие
результаты допустимо использовать при ошибке. Не вводи интерфейс, если
потребителю достаточно конкретного типа. В reference показано, когда нужен
`io.Reader`, а когда связь типов лучше выразить параметром типа. Сохраняй
формат `gofmt` и не меняй версию Go ради примера.

Если работу выполняет subagent, явно передай ему нужный скилл, правила проекта,
область изменений и критерии результата. Не предполагай, что он автоматически
наследует все инструкции родительской сессии.

## 8. Обновляй и удаляй по запросу

Обновляй только выбранные пользователем пакеты. Зафиксируй новую ревизию,
сравни изменения инструкций и ресурсов, сохрани локальные адаптации, затем
повтори проверку установки. Не обновляй скиллы незаметно во время обычной задачи.

При удалении установи точный путь и область. Удали только запрошенный пакет;
не затрагивай исходный репозиторий, другие skills и резервные копии без отдельного
указания. После удаления проверь discovery или объясни необходимость обновить
сессию.
